# StalkShift — план разработки

Дата исследования: 2026-09-05. Статус: Rust-мост и DLL поддерживают поворотники, кольцо света, дальний/мигание и передние дворники. Поворотники, пауза/USB и свет подтверждены в ETS2 1.60.1.7; проверка дворников продолжается. Публичный репозиторий: https://github.com/Moltenship/stalkshift.

## Цель и объём первой версии

Создать самостоятельный open-source мост для MOZA Multi-function Stalks: физические положения переключателей управляют соответствующими функциями ETS2 предсказуемо, в том числе после паузы и переподключения.

Подтверждённый пользователем объём: ETS2 на Windows, все функции существующего моста в первой версии, включая автоматическую подстройку круиза под ограничение скорости. Промежуточные прототипы выпускаем поэтапно, но они не означают завершение первой версии. ATS и дополнительные устройства — за её пределами. Windows x64 и Steam остаются рабочими предположениями; конкретные версии фиксируем перед испытаниями.

MOZA Multi-function Stalks подключён напрямую по USB: `346e:0024`, интерфейс 2, отчёты по 8 байт. Положения поворотника, кольца света и маленького колёсика передних дворников передаются импульсами, а движение левого рычага к себе/от себя — удержаниями. Эти разные правила проверяются на четырёх аппаратных записях с сохранёнными поправками пользователя. Режим — Multi function key switch direct, Pit House 1.4.0.30 по сообщению пользователя; отдельная версия прошивки неизвестна. Подробности: [наблюдения устройства](docs/hardware-observations.md) и [интеграция с игрой](docs/game-integration.md).

Публикуемый результат: исходники программы и плагина, описание протокола устройства, тестовые записи ввода, инструкция сборки, готовый portable-релиз. Собственный код публикуется под MIT. Код пишем самостоятельно; существующий мост служит ориентиром по поведению.

## Что подтверждено источниками

- [Репозиторий существующего моста](https://github.com/JacKJodel23/MOZA-Truck-Stalk-Bridge) прямо сообщает, что исходники приложения не опубликованы. Заявленная интеграция: Windows HID, SCS Input SDK и Telemetry SDK. VID/PID `346E:0024` — ориентир автора, подлежит проверке на нашем устройстве.
- [Тема автора](https://forum.scssoft.com/viewtopic.php?t=353055) описывает управление переключателями и известную проблему начальной синхронизации селектора. На момент просмотра тема описывает 1.4.1, README — исправления связи в 1.4.2. Заявления автора не являются нашей аппаратной проверкой.
- [Официальная страница SCS](https://modding.scssoft.com/wiki/Documentation/Engine/SDK/Telemetry) предоставляет [SDK 1.14](https://download.eurotrucksimulator2.com/scs_sdk_1_14.zip), включая Input API и примеры.
- Проверены файлы официального архива: `scssdk_input_device.h`, `scssdk_input_event.h`, `scssdk_telemetry_truck_common_channels.h`, `readme.txt`. Семантические входы сопоставляются с игровыми mixes по имени; поддерживается лишь часть mixes. Подсказка SDK — соответствующие `semantical.*` в свежем `controls.sii`. Callback ввода работает в главном потоке игры и должен выполняться быстро.
- `truck.lblinker`/`truck.rblinker` описывают логическое включение поворотников, а `truck.light.lblinker`/`truck.light.rblinker` — текущую фазу лампы. Для синхронизации нужны первые. `truck.wipers` в SDK — только bool, точный режим дворников этим каналом не наблюдается.
- [Инструкция MOZA](https://support.mozaracing.com/en/support/solutions/articles/70000669136-multi-function-stalk-configuration-guide) описывает адаптацию через заданные клавиатурные назначения. Для нашего пути потребуется исключить двойную обработку устройства.
- [TruckTel](https://github.com/jvanstraten/TruckTel/blob/main/doc/api.md) публикует результаты исследования семантических входов. Его таблица — источник кандидатов для проверки, не гарантия поведения текущей ETS2. В частности, проверить `lblinkerh`/`rblinkerh`, `lightoff`/`lightpark`/`lighton`, `wipers0`–`wipers4`.

Context7 проверен двумя запросами; подходящей официальной документации SCS в результатах нет. Выводы об SDK основаны на официальном архиве.

## Предлагаемая архитектура

```text
MOZA HID → декодер → нормализованное состояние → логика управления
                                                    ↕
                                           локальная связь
                                                    ↕
                                  DLL: SCS Input + Telemetry ↔ ETS2
```

1. **Чтение устройства.** Обнаружение HID-интерфейса, чтение reports, отслеживание подключения. Выбор интерфейса по дескриптору/usage/report ID, а не только VID/PID. Сохранение исходных reports с временными метками для воспроизведения.
2. **Декодер.** Перевод reports в именованные положения, удержания и одноразовые события. Полный снимок состояния отличается от события изменения. Сопоставления документируются отдельно для проверенных режимов/прошивок.
3. **Логика управления.** Отдельный модуль без зависимости от физического устройства и интерфейса приложения. Учитывает состояние игры, задержку подтверждения и правила повторного подключения.
4. **Игровой плагин.** Минимальная DLL с Input и Telemetry API. Регистрирует только нужные входы. Чтение HID, ожидание IPC и запись файлов не выполняются в callbacks игры. Отдельно проверяем загрузку и завершение обеих API в одной DLL.
5. **Связь.** Реализован Windows named pipe, протокол v2 по 40 байт с идентификатором сеанса, номером сообщения и эпохой готовности. Плагин самостоятельно ограничивает срок команды; устаревшие ответы после паузы/нового сеанса отбрасываются. Конфликтующие положения одной группы запрещены. Получение сообщения плагином не означает, что игра уже выполнила действие.
6. **Диагностика.** Сначала консоль: состояние устройства, игры, декодированные входы и отправленные действия. Позже небольшое окно/трей с настройками и экспортом журнала.

Принятый стек: Rust для DLL, утилиты HID и логики моста в одном Cargo workspace. Реализованы `stalkshift` (CLI), `stalkshift-hid` (Windows HID), `stalkshift-capture` (записи), `stalkshift-core` (декодеры), `stalkshift-protocol` (IPC и ограничение команд) и `stalkshift-plugin` (DLL). UI-фреймворк пока не фиксируем.

- DLL собирается как `cdylib` с экспортами и структурами, соответствующими C ABI SCS. Rust поддерживает [системные динамические библиотеки](https://doc.rust-lang.org/reference/linkage.html) и [FFI](https://doc.rust-lang.org/nomicon/ffi.html). Слой FFI должен явно контролировать размеры/выравнивание, время жизни callback-контекстов и обработку panic внутри границ вызова. Rust не изолирует ошибку DLL от процесса игры.
- Для чтения HID кандидат — [`hidapi`](https://docs.rs/hidapi/latest/hidapi/) с `windows-native`, обращающимся к Windows HID API без C-библиотеки HIDAPI. Поддержку необходимых операций проверяем прототипом на MOZA.
- [`scs-sdk-crates`](https://github.com/AptS-1547/scs-sdk-crates) — сторонний кандидат на слой SCS: автор заявляет поддержку Input/Telemetry и предоставляет примеры. До принятия зависимости проверяем код, лицензию, соответствие официальным заголовкам и совместную работу обеих API в нашей DLL. Альтернатива — небольшой собственный Rust FFI-слой для используемой части SDK.
- Предлагаемые модули: `stalk-core` (декодер и правила), `stalk-hid` (устройство и запись), `stalk-protocol` (IPC), `scs-plugin` (DLL), `stalk-app` (процесс моста и диагностика). Основная логика остаётся безопасным Rust вне FFI и тестируется на записях устройства.

## Правила поведения

- Фиксированные положения, краткие нажатия и удержания имеют разные правила. Повтор одинакового HID-report не должен повторять toggle-действие.
- Для положения переключателя вначале ищем прямой семантический вход. Если доступен только toggle, используем телеметрию, ожидание результата и ограничение попыток. Отсутствующие данные не считаются значением false.
- Предварительно для света и дворников физическое положение имеет приоритет при синхронизации. Поведение после ручного изменения в игре и автосброса поворотника проверяем и согласуем отдельно, чтобы избежать борьбы источников ввода.
- MIST должен давать один цикл на вход в положение, если это подтверждённо реализуемо. Задержка фиксированной длины сама по себе не доказывает ровно один цикл.
- При потере устройства или связи сбрасываем удерживаемые виртуальные входы. Плагин сам отслеживает heartbeat, даже если программа зависла. При неактивном вводе игры сброс применяется при первой возможности callback.
- После паузы/переподключения требуется свежий снимок. Одноразовые действия не воспроизводятся повторно. Для D/R и включения круиза предварительно требуется новое действие пользователя; автоматическое восстановление света/дворников проверяется отдельно.
- Пауза, загрузка, отсутствие грузовика и неактивный Input API — отдельные состояния. Не предполагаем, что одного флага паузы достаточно для всех меню и потери фокуса.
- В базовой конфигурации отключаем адаптивные клавиатурные команды Pit House и прямые назначения stalks в игре. HidHide остаётся дополнительным вариантом; поведение при его использовании проверяется отдельно.
- Автоматическая подстройка круиза входит в первую версию как отключаемая функция. Она изменяет только целевую скорость круиза. При неактивном круизе, отсутствующем/устаревшем ограничении или неготовой игре команды не отправляются. Ручная команда прерывает текущую подстройку; отсутствие результата ограничивает число попыток; переход через недостижимую цель не вызывает колебаний. После разрыва связи режим требует повторного включения.
- Для первоначального паритета автоматического круиза планируем поддержать ETS2 с километрами и шагом 5 км/ч; интервал команд 300 мс — исходный ориентир существующего моста, подлежащий проверке. Настройки явно указываются в программе и инструкции; другие комбинации не считаются поддержанными без испытаний.

## Этапы и критерии завершения

| Этап | Работа | Проверяемый результат |
|---|---|---|
| 0. Карта устройства | Снять HID-дескриптор и записи каждого положения, комбинаций, удержаний и подключения при уже отклонённом рычаге | Опубликована таблица reports → состояния; записи повторно декодируются одинаково |
| 1. Проверка SCS | Минимальная DLL, синтетические входы без устройства, телеметрия; проверить поворотники, свет и прямые режимы дворников | Рабочая матрица входов на конкретной версии ETS2; понятны ограничения и влияние регистрации входов на другие назначения |
| 2. Первый сквозной прототип | Физический левый рычаг → программа → DLL → поворотники | Лево/центр/право работают многократно; отключение USB и остановка программы не оставляют удержание; клавиатура и руль проверены |
| 3. Основные переключатели | Свет, дальний/мигание, дворники, аварийка, клаксон; обработка состояния игры | Пройден сценарий запуска, паузы, загрузки сохранения и переподключения для каждой функции |
| 4. Полная поддержка управления | Обычный круиз, повтор +/- при удержании, D/N/R/P и стояночный тормоз | Проверены переходы селектора и конфликтующие команды. Для первой реализации селектора предварительно поддерживается Real Automatic; P моделируется как N + стояночный тормоз |
| 5. Автоматическая подстройка круиза | Включение режима переключателем, движение цели к навигационному ограничению, остановка при ручном вмешательстве и отказе игры | Проверены рост/снижение лимита, отсутствие лимита, неактивный круиз, непредставимая цель, ограничитель грузовика, пауза и потеря связи; нет бесконечных повторов и колебаний |
| 6. Первая публичная версия | Все функции этапов 2–5, минимальный интерфейс, конфигурация назначений, установка/удаление DLL, сборка в CI, документация | Из чистого checkout собираются приложение и DLL; portable-пакет устанавливается по инструкции и проходит аппаратный прогон всего набора функций |
| Позже | ATS, дополнительные устройства | Отдельные критерии и матрица совместимости |

Не обещаем сроки функционального паритета до завершения этапов 0–1: неизвестны reports конкретной прошивки и реальное поведение нужных входов ETS2.

## Проверки

- Автоматические: декодирование записанных reports; переходы состояний; повтор reports; задержанная/отсутствующая телеметрия; разрыв связи; смена сеанса; устаревшие сообщения; завершение удержаний и отмена повторов круиза.
- В игре: запуск с каждым фиксированным положением, пауза/возврат, загрузка сохранения, смена грузовика, отключение USB, перезапуск программы, быстрое переключение противоположных положений, сочетание с рулём/клавиатурой и Pit House.
- Дворники: один взмах MIST подтверждён пользователем на стандартном Mercedes-Benz New Actros StreamSpace после исправления 2026-09-05. Остаётся визуально проверить различия INT / LO / HI и работу на других грузовиках, поскольку bool-телеметрии недостаточно для подтверждения скорости/полного цикла.
- Автоматический круиз: воспроизводимые последовательности лимитов и подтверждений цели, задержки телеметрии, неподдерживаемые настройки, ручное вмешательство, отказ игры менять цель и отсутствие колебаний возле границы шага. Затем аппаратная проверка в ETS2.
- Надёжность: предложенный критерий перед релизом — трёхчасовой аппаратный прогон с несколькими переподключениями; оценить память, очередь, задержки и размер логов.
- Установка: затрагивает только файлы проекта; существующие плагины и конфигурации сохраняются. Совместимость с другими установленными плагинами проверяется на фактическом наборе пользователя.

## Ближайшие решения

1. Какие версии Windows/ETS2/Pit House/прошивки используются? Уточнить перед испытаниями; наличие USB-устройства подтверждено.
2. Выбрать UI-фреймворк после проверки HID и SCS; язык Rust уже принят, собственный код опубликован под MIT.
3. Нужно ли повторить назначения существующего моста буквально либо выбрать собственную схему, особенно для правого рычага и круиза? До уточнения исходная схема служит предлагаемым профилем по умолчанию.

Первая реализационная задача после обсуждения: подготовить утилиту записи HID и матрицу возможностей SCS, затем попросить пользователя подключить stalks и пройти запись положений. Карту MOZA не считать подтверждённой до аппаратных записей.
